*** Architecture decisions :
 1) first the server was thread per connection, which proved practically useless under any load.
 
 2) second I developed a custom made threadpool with the number of threads equal to hardware threads:
    - Before solving the Nigel alogorithim setting the server refused most connections above 1k.

    - After solving it the server could serve up to 800-900 concurrent users before it starts failing.
    
    - after investigation found that due to the nature of blocking networking functions, the threds spend
      most of their time sleeping, on a pool of 12 threads this is very low performant ( 1k req / sec or so)
    
    - the solution I found was either switch to IOCP functions ( big architecture change since i didnt know       about them before starting ) or another one i developed.
    
    - basically trying to get the best of both worlds, increasing throughput while leaving cpu context swi-
      tching as low as possible.
    
    - I steadly increased the number of threads in the pool by a factor determined imprically through multi-
      runs, Basically binary searching from a factor of 5 to 100, which had the best performance.
    
    - landed on 50 ( although the result was tailored on one machine it still performs well on machines with similar specs, still IOCP or epoll is still superior )

    
    - through this solution i reached about 10k req/sec steadily, and able to support about 12k users.


    - then found 2 potential bottlenecks, accuiring the logs Queue mutex to push into it and constanly
      using windows file-access functions ( very slow as they anti-virus scan them before opening )

    - for the first I commented logging when benchmarking.

    - for the second I built a custom made cache that lazily loads a file into memory the first time it           serves it.

    - file caches are emptied when edicted or deleted but not when the cahce gets big ( potenital impro-
      vment )
    
    - Through these changes we reached around 70k req/sec surpasing Apache on most configurations that 
      require feasible amounts of RAM to test


*** When testing with big files, Apache outperforms myServer under low connections count but mine 
     outperforms under higher, I suppose that happens since my caching system relies on User-space send 
     functions which forces the thread to keep looping until the file is fully-sent
     while Apache uses kernel-space send which send the file much faster.

     - a fix might be to instead of caching the file bytes we cache the file handles, so windows itself
       is the one responsible for sending the files, and when a new connection want to send a file thats 
        handle was cached, it can just call windows kernel-level send diretly without needing to reopen
        the file.
